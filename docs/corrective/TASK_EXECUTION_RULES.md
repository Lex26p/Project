# Dispatcher — общий контракт выполнения корректирующих заданий

## 1. Роль исполнителя

Исполнитель — модель высокого уровня с локальной технической автономией. Она отвечает за законченную реализацию задания, тесты и честный отчёт.

Архитектурные границы задаются `CORRECTIVE_ARCHITECTURE_SPECIFICATION.md` и конкретным task-файлом. Внутри них исполнитель самостоятельно выбирает структуру классов, методы, вспомогательные типы и разумный связанный рефакторинг.

## 2. Контекст

Перед началом читать:

1. текущий task-файл;
2. указанные им разделы архитектурной спецификации и ADR;
3. перечисленные отправные файлы.

Остальные файлы изучать по необходимости. Не требуется предварительно читать весь проект, все задания или всю историческую документацию.

Если фактический код отличается от описания, сначала определить, влияет ли отличие на цель. Локально совместимое отличие учитывается в реализации; архитектурное противоречие выносится как blocking decision.

## 3. Допустимая автономия

В пределах цели разрешено:

- создавать, изменять и удалять локально устаревшие implementation-типы;
- добавлять project references и package references, если они необходимы и согласуются с C#/.NET baseline;
- менять composition root и конфигурацию;
- добавлять migrations только новой версией;
- добавлять unit, integration, process и browser tests;
- выполнять связанный рефакторинг;
- обновлять документацию, непосредственно изменённую заданием.

Не нужно спрашивать разрешение на каждый дополнительный файл.

## 4. Неподвижные границы

- Windows 11 и PostgreSQL 17.
- Без Docker и Linux-проверок.
- Без физической записи Modbus/SNMP.
- Без нового broker, loopback service API или второго production database technology.
- Без передачи secret в query string, Web payload, log или test fixture.
- Без автоматических migrations при обычном старте RuntimeHost/Server.
- Без ослабления authorization, session validation и owner boundaries.
- Без превращения provisional product areas в выдуманный публичный API.
- Без переноса на C++.

## 5. Работа со сторонними проблемами

- Если проблема непосредственно блокирует заданный результат и исправление локально, её можно исправить и указать в отчёте.
- Если исправление меняет архитектуру или заметно расширяет объём, остановиться и описать: факт, влияние, минимальные варианты и рекомендуемое решение.
- Не выполнять широкую «чистку проекта» попутно.

## 6. Качество

Каждая задача обязана:

- сохранить nullable/analyzer/warnings-as-errors baseline;
- использовать cancellation и bounded resource limits в длительных операциях;
- проверять успешный и отказный сценарии;
- не скрывать ошибки пустыми catch;
- сохранять idempotency/replay там, где есть durable state;
- не раскрывать конфигурацию и secrets в сообщениях об ошибках.

## 7. Общая проверка

Из корня проекта:

```powershell
dotnet restore Dispatcher.slnx --locked-mode
dotnet build Dispatcher.slnx -c Release --no-restore
dotnet test tests\Dispatcher.UnitTests\Dispatcher.UnitTests.csproj -c Release --no-build
dotnet test tests\Dispatcher.IntegrationTests\Dispatcher.IntegrationTests.csproj -c Release --no-build
```

Если задание добавляет process/browser/lab tests, выполнить также команды из task-файла. Не исправлять несвязанный внешний сбой молча: отделить его от регрессии задания.

## 8. Итоговый отчёт

Отчёт содержит:

1. достигнутый результат;
2. изменённые и созданные файлы по группам;
3. ключевые implementation decisions;
4. выполненные проверки и точный результат;
5. проверенные отказные сценарии;
6. оставшиеся ограничения или blocking decisions.

Пересказ задания и подробный журнал каждого шага не нужны.

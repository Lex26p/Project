# Dispatcher — корректирующая программа

**Статус:** актуальная точка входа для работ после S38  
**Среда текущего этапа:** Windows 11, PostgreSQL 17, C#/.NET  
**Дата:** 26 июля 2026 года

## 1. Назначение

Этот каталог отделяет корректирующую программу от исторической последовательности S01–S38. Старые задания не переписываются: они подтверждают созданный доменный и тестовый baseline, но не доказывают производственную композицию процессов.

Корректирующая программа закрывает следующие разрывы:

- фактический запуск источников и polling в `Dispatcher.RuntimeHost`;
- устойчивый канал RuntimeHost → PostgreSQL → Server;
- автоматическую цепочку History → Alarm → Event;
- производственную web-сессию, realtime и same-origin hosting;
- завершённые основные web-сценарии;
- read-only работу Modbus TCP и SNMP;
- эксплуатацию на Windows 11 и итоговую приёмку.

## 2. Состав

- `CORRECTIVE_ARCHITECTURE_SPECIFICATION.md` — целевая архитектура и обязательные инварианты.
- `CORRECTIVE_ROADMAP.md` — порядок задач, зависимости и контрольные точки.
- `TASK_EXECUTION_RULES.md` — общий контракт младшей модели.
- `STATUS.md` — состояние выполнения.
- `tasks/C01_...C23_...` — полные задания на реализацию и приёмку.

## 3. Приоритет документации

При противоречии применяется следующий порядок:

1. Последняя явная инструкция пользователя.
2. Эта корректирующая спецификация и относящееся к работе задание.
3. Принятые ADR в `docs/`.
4. `DISPATCHER_MASTER_IMPLEMENTATION_SPECIFICATION.md` и действующие семантические контракты.
5. Фактический код и тесты как свидетельство текущей реализации.
6. Исторические roadmap и sprint catalog.

Продуктовая концепция определяет назначение и пользовательский смысл. `WEB_INTERFACE_SPECIFICATION.md` и `WEB_BACKEND_API_REQUIREMENTS.md` определяют целевое поведение Web. Технические решения из старых концептуальных документов не переопределяют C#-first baseline и эту корректирующую программу.

Эти три больших нормативных документа находятся во внешнем пакете `Dispatcher-Handoff/normative`, который передаётся вместе с проектом. Исполнитель UI-задачи должен найти документ по имени; копировать в контекст весь старый архив не требуется.

## 4. Как выдавать задание младшей модели

Младшей модели передаётся:

1. `TASK_EXECUTION_RULES.md`;
2. один файл из `tasks/`;
3. перечисленные в нём разделы архитектурной спецификации и ADR;
4. указанные отправные файлы проекта.

Читать все задания, всю документацию или весь проект не требуется. Другие файлы изучаются по необходимости.

Модель высокого уровня самостоятельно выбирает локальную структуру реализации, добавляет необходимые тесты и выполняет связанный рефакторинг. Она не должна самостоятельно расширять продуктовую или архитектурную границу задания.

## 5. Правило выполнения

- По умолчанию задания выполняются по номеру.
- Следующее задание начинается после выполнения критериев предыдущего.
- Обнаруженный сторонний дефект исправляется только если он непосредственно блокирует текущую цель; иначе он фиксируется в отчёте.
- Реальная физическая запись на Modbus/SNMP устройства не разрешена ни одним заданием.
- `C23` является условным анализом. Он не разрешает перенос на C++.

## 6. Что считается завершением программы

Программа завершена только когда:

- Simulator проходит межпроцессный E2E;
- Server и Web получают current/history/alarm/event из производственного PostgreSQL-контура;
- реальные Modbus TCP и SNMP устройства прошли read-only лабораторную проверку;
- Windows installation/start/restart/backup/restore задокументированы и проверены;
- итоговый fault/soak corpus пройден без необъяснимого роста ресурсов и потери обязательных данных.

Прохождение существующих модульных и интеграционных тестов само по себе не завершает программу.
